# Flatcap for WezTerm: full mapping

Reference for [Flatcap for WezTerm](../README.md). The tables are generated by `python3 scripts/build.py` from `src/theme.json`; do not edit them by hand.

Colors are resolved by **meaning**, never by position or by nearest hex. Every value comes from [`src/theme.json`](../src/theme.json) (Flatcap 2.0.0). WezTerm's key names were checked against the [color scheme documentation](https://wezterm.org/config/appearance.html), the pages of the individual `config.*` options and the `Palette`/`TabBarColors` definitions of the 20240203 source; the generated TOML was loaded by WezTerm itself and every key came back with the expected value (see [Validation](#validation)).

## What ships, and why two mechanisms

| File | Carries | Reaches WezTerm as |
| :--- | :--- | :--- |
| `colors/Flatcap Slate.toml`, `colors/Flatcap Daylight.toml` | The whole `[colors]` palette, tab bar colors and `[metadata]` | A color scheme (`color_scheme`, `color_scheme_dirs`) |
| `plugin/init.lua` | The same two schemes **plus** what a scheme cannot carry | `config.color_schemes`, `config.colors.tab_bar`, `config.window_frame`, `command_palette_*`, `char_select_*` |

A color scheme file only contains `[colors]` and `[metadata]`. The window frame (title bar, window buttons), the command palette and the character selector are separate `config.*` options, so only the plugin can theme them.

Notes:

- **Cursor.** `cursor_bg`/`cursor_border` use `accent.fill` and `cursor_fg` uses `accent.on`, the pair Flatcap uses for filled controls. The text cursor is not `focus.ring`: focus and the text cursor are independent signals. `cursor_border` is the color of a bar or underline cursor.
- **Selection is a full pair.** WezTerm supports `selection_fg`, so `selection.fg` / `selection.bg` are both applied (Windows Terminal cannot). The cost is that selected text is drawn in one color: syntax colors disappear inside a selection. The alternative, `selection_fg = 'none'`, keeps each cell's own color, but some ANSI colors would then fall below 4.5:1 on the selection fill, so Flatcap does not use it.
- **Copy mode and Quick Select** use the accent pair for the active/hint element and neutral fills for the rest. In copy mode the active highlight only shows after the selection was extended with the mouse; otherwise `selection_*` applies (WezTerm's rule).
- **Scrollbar thumb and pane divider** are functional marks, so they use `border.control`, not the decorative `border.subtle`. WezTerm draws the scrollbar only when `enable_scroll_bar` is on.
- **`visual_bell`** is the background flash of the visual bell (`visual_bell` is only visible when the bell is configured as a visual one). It uses `info.bg`: feedback, quiet. The flash is a low-contrast, short change by design.
- **`compose_cursor`** (IME / dead key / leader key pending) uses `warning.fg`: a pending state, distinguishable from the normal cursor by hue.

- **The fancy tab bar ignores the scheme's `tab_bar`.** In WezTerm 20240203 the native (fancy, default) tab bar reads `config.colors.tab_bar` directly, while the retro bar reads the colors of the selected scheme (source: `build_fancy_tab_bar` vs `TabBarState::new`). The plugin therefore copies the scheme's `tab_bar` into `config.colors.tab_bar`. With the TOML alone the retro tab bar is themed and the fancy one is not; the README shows the one-line fix. Other `config.colors` keys are left alone.
- **Fancy tab bar background.** The strip behind the tabs is `window_frame.active_titlebar_bg` / `inactive_titlebar_bg`, not `tab_bar.background` (which the retro bar uses). Both are `bg.surface`.
- **The current tab is told apart by fill only.** `intensity = Bold` is meant for the retro tab bar; in the fancy one it was not observed to have an effect (the source builds the fancy tab title from the tab's own text attributes, not from `intensity`). The active tab fill is `bg.selected`, the selected-state role, which reads as a quiet blue tint against the `bg.surface` bar. Window-level options cannot add a second indicator, so this is a known limitation (see the ratio of the two fills in the informational table below).
- `inactive_tab_edge_hover` exists in the source but not in the documentation, so it is not set.

- **`window_frame` is merged, not replaced.** Keys you set before calling `apply_to_config` that Flatcap does not touch (borders, `font_size`) survive; keys Flatcap sets are overwritten, so put your overrides after the call.
- The title bar is only drawn where WezTerm draws it: with `window_decorations = 'TITLE | RESIZE'` on Wayland client-side decorations, with `INTEGRATED_BUTTONS`, and as the fancy tab bar strip. With native OS title bars, the OS draws them.
- The command palette selects a row by swapping its foreground and background, so the selected row has the same contrast as the palette text.
- **`inactive_pane_hsb` is not set.** WezTerm's default (saturation 0.9, brightness 0.8) keeps default text well above target in an inactive pane (see the informational table), so there is no accessibility reason to override it. It does make inactive panes a gray the palette does not define, most visibly in Daylight; if you prefer a gentler dimming, set `config.inactive_pane_hsb` after the plugin call.

Decisions behind the table, shared with [Flatcap for Windows Terminal](https://github.com/cheycron/flatcap-windows-terminal) (same terminal semantics, **no deviation in the role mapping**):

- **The six hues keep their meaning.** Red, green, yellow, blue, purple (ANSI magenta) and cyan map to feedback and syntax roles. The six categorical `data.*` colors are chart series, so they are not used here.
- **Bright is not neon.** Flatcap has no separate bright tier. Blue uses the stronger step of the accent ramp. The other hues repeat their normal role, so `ESC[91m` and `ESC[31m` look the same. No value was invented to fill the gap.
- **Black and bright white follow luminance; white is ink.** Programs use black (0) and bright white (15) as block backgrounds and as text on colored blocks, so black stays dark and bright white stays light in both modes. In Slate, black is the quiet border tone: visible as a block on the canvas, not meant for reading text on it. In Daylight, bright white is the raised white surface. ANSI white (7) is `text.secondary` in both modes because TUIs use it as ordinary text.
- **Bright black is dimmed text, not black.** Shells draw suggestions and comments with it, so it uses the muted text role.
- **WezTerm key names.** WezTerm lists `ansi` and `brights` as two arrays of eight, in index order, so the table above is the index order of those arrays.

What differs from Windows Terminal is not the mapping but the host: WezTerm has `selection_fg`, a separate bold behavior (below), and named color keys the other host lacks.

- **Increased contrast.** The `contrast.*` roles of the core are not applied: WezTerm has no contrast preference to switch on, and `system` mode only maps the OS light/dark setting (including the `HighContrast` appearance values) to Slate or Daylight.

## Limitations and behavior to know

- **Bold brightens ANSI 0–7 by default.** WezTerm's `bold_brightens_ansi_colors` defaults to on (`BrightAndBold`): bold text in ANSI 0–7 uses the matching 8–15 color. With this mapping that means bold ANSI white becomes `brightWhite`, which is the raised white surface in Daylight, and bold ANSI black becomes `brightBlack`. Bold white text is therefore (nearly) invisible in Daylight under the default. Flatcap does not change a behavior option; if a tool you use hits this, set `config.bold_brightens_ansi_colors = 'No'`. In Slate the same substitution is harmless.
- **The plugin changes only color options (and fonts if you ask).** It never sets opacity, backdrop, blur, key bindings, font sizes or `front_end`.
- **Opacity and backdrop change the colors you see.** `window_background_opacity` below 1.0, `win32_system_backdrop` (Acrylic, Mica) and `macos_window_background_blur` blend the desktop into the background, so none of the contrast figures hold. Flatcap is matte: use an opaque window.
- **Fancy tab bar.** See above: the tab bar colors come from `config.colors.tab_bar`, and the active tab is told apart by fill only.
- **Nightly-only keys** (`compose_fg`, `compose_bg`, `input_selector_label_*`, `launcher_label_*`) are not set: they do not exist in 20240203 and were not tested.
- **16 colors, plus whatever your tools emit.** See the list above.

## Validation

Done, with WezTerm `20240203-110809-5046fc22` (Linux AppImage), on Linux:

- Contrast of every pair in the table above, from the generated values (`--check`).
- Both TOML files parse with Python's `tomllib`, and the parsed `[colors]` equals the model they were generated from.
- Both TOML files were loaded by WezTerm (`wezterm.color.load_scheme`) and every key of the model came back set with its expected value. WezTerm ignores unknown keys in a scheme file, so this round trip, not a clean load, is the evidence that the key names are right.
- The plugin was loaded through `wezterm.plugin.require` with a `file://` URL in `system`, `slate` and `daylight` modes, with an unknown mode (warning, falls back to `system`), and with `fonts = true`, with a pre-existing `window_frame` key preserved. It was loaded by the `wezterm-mux-server` process, where `wezterm.gui` is absent, and fell back to Slate.
- The plugin and the example were syntax-checked with `luac5.4`.
- Screenshots in a real `wezterm start` under Xvfb (`front_end = 'Software'`, the software renderer, no GPU): the fancy tab bar with three tabs, splits, the command palette, Quick Select, search highlights and a mouse selection, in both modes; git log and diff, `ls`, `bat --theme=ansi`, an ANSI grid and log-style lines as content.

Not done:

- **Windows and macOS.** Nothing was run on either. The Windows-specific facts (config and scheme directories, `INTEGRATED_BUTTONS`) come from the documentation.
- **Hardware rendering.** `WebGpu` and `OpenGL` front ends, real GPUs, HiDPI scaling and font rendering differences were not tested.
- **Follow-the-system switching in a real desktop.** `wezterm.gui.get_appearance()` was exercised in a bare X11 session, where it reports `Light`; switching between light and dark in GNOME, KDE, macOS or Windows was not observed. The mapping from the returned strings is a documented, unit-sized function (`mode_for_appearance`).
- **Other WezTerm versions.** Older builds, newer stable builds and nightly were not run.
- **Other plugins.** Loading Flatcap together with `wezterm-agent-deck` was exercised (see the README); other plugins were not.
- **Real programs under the scheme.** Only the programs listed above. vim, htop, mc, lazygit and similar TUIs were not exercised, nor were Nerd Font glyphs, box drawing or ligatures.
- **Assistive technology and users.** Nothing beyond contrast ratios and screenshots.

Color scheme directories: `$HOME/.config/wezterm/colors` on POSIX systems; on Windows the documentation names a `colors` directory next to `wezterm.exe`. `config.color_scheme_dirs = { path }` works everywhere and is what the README uses.

## Fonts

- Use the **exact installed family name**. `Cascadia Code NF` (from the Cascadia releases) and the Nerd Fonts build `CaskaydiaCove Nerd Font Mono` are different families and are not interchangeable.
- `fonts = true` in the plugin sets `config.font = wezterm.font('Cascadia Code')` and `window_frame.font = wezterm.font { family = 'IBM Plex Sans', weight = 'Medium' }`. Neither font is bundled or installed; WezTerm falls back (and says so in its log) when a family is missing. Cascadia Code and IBM Plex Sans are SIL OFL 1.1.
- WezTerm does not expose per-region ligature control. To turn ligatures off for logs and literal reading, use `config.harfbuzz_features = { 'calt=0', 'clig=0', 'liga=0' }`, or pick the Mono family.
- The line height is left at WezTerm's default: the Flatcap code line height suits editors, while a terminal needs contiguous cells.

## Rebuilding

```sh
python3 scripts/build.py              # regenerate the schemes, the plugin and the generated blocks
python3 scripts/build.py --check      # fail if any of them is stale or a contrast target is missed
python3 scripts/build.py --check --lua  # also syntax-check the Lua files (needs luac5.4 or luac)
python3 scripts/build.py --sync       # refresh src/theme.json from ../00-Flatcap, then rebuild
python3 scripts/build.py --contrast   # print the full contrast report, including the 16x16 matrix
```

`--sync` expects the core checkout next to this repository (`../00-Flatcap`); pass a path to use another one. Python 3.10 or newer, standard library only (on 3.10 the TOML re-parse check is skipped because `tomllib` arrived in 3.11).
